## Summary

The crate compiles and its current unit tests pass, but the durability contract is not reliable under process crashes, concurrent writers, or several public mutation APIs. The most urgent work is to make startup compaction recoverable, serialize each logical mutation across both the WAL and in-memory state, and ensure every public mutation is represented in the WAL.

## P1 — High priority

### 1. A crash during startup compaction can make the next startup discard the only complete WAL

Locations: `src/key_value_store.rs:27-55`, `src/key_set_store.rs:29-67`, `src/key_map_store.rs:31-78`

Each `init_new` renames the live WAL to a hidden temporary file, immediately creates a new empty live WAL, replays into it, and only then removes the temporary file. If the process exits after the rename or during replay, the next startup looks only at the new live filename and ignores the still-complete hidden file. An empty or partially replayed live WAL can therefore replace all previously committed data.

Make recovery a state machine that recognizes both filenames. Build and `sync_all` a complete replacement before atomically publishing it, sync the directory around renames, and remove the source only after publication is confirmed. Add crash-injection tests for every boundary in this sequence.

### 2. Set/map `compute*` mutations are never written to the WAL

Locations: `src/key_set_store.rs:149-199`, `src/key_map_store.rs:373-417`

`compute`, `compute_async`, `compute_if_present`, and `compute_if_absent` directly mutate the `HashSet`/`BTreeMap` stored in `DashMap` but append no corresponding WAL actions. The changes are visible until the process restarts and then silently disappear; these methods can also create an empty outer key that cannot be reconstructed.

Record the before/after delta while the entry is locked, or redesign the callback to return an explicit mutation that can be logged before it is published. Ensure empty-key deletion is logged as well.

### 3. WAL order and in-memory order can diverge under concurrent mutations

Locations: `src/key_value_store.rs:83-86`, `src/key_set_store.rs:115-147`, `src/key_map_store.rs:134-175`

Most methods append to the globally locked WAL, release that lock, and only afterward acquire/mutate the relevant `DashMap` entry. Two threads can therefore append `put(v1)` then `put(v2)` but apply the map updates as `v2` then `v1`. The live store returns `v1`, while replay returns `v2`. Append/remove races in the set and sorted-map stores have the same problem.

Treat the WAL append and in-memory update as one ordered operation. Use one consistent lock order for every mutation (including callbacks and delete-on-empty paths), or assign a transaction/sequence lock that remains held until both representations are updated. Add a deterministic interleaving test that pauses between append and map update.

### 4. A normal crash that leaves a partial final record prevents the database from reopening

Locations: `src/wal/mod.rs:137-163`, `src/wal/mod.rs:167-260`, `src/wal/mod.rs:263-292`, `src/wal/mod.rs:306-371`

`build_action` performs unchecked slices and `unwrap`s for every field. `prev_block_start_offset` also subtracts and slices before it can return `Err`. Because a WAL record is emitted through several separate writes, process termination can leave a truncated header, payload, or footer. All three file-backed stores then panic during startup rather than replaying the complete prefix. The key/value fallback does not help because these bounds failures panic before an `Err` is returned.

Make frame parsing return a structured error after checked length/offset arithmetic. Treat an incomplete trailing frame as an uncommitted tail that can be ignored/truncated, while reporting CRC or structural corruption inside the committed prefix. Exercise every possible truncation point in tests.

### 5. Successful mutations are not guaranteed to be durable on disk

Location: `src/wal/mod.rs:122-128`

The write path calls `Write::flush`, but for `std::fs::File` that does not provide the `fsync`/`fdatasync` durability barrier required before acknowledging a durable mutation. A power loss can therefore remove operations that already returned successfully. Startup compaction has the same publication problem.

For the file-backed implementation, call `sync_data` or `sync_all` according to the documented durability contract, propagate I/O failures to callers, and sync the containing directory when creating or renaming WAL files. If weaker durability is intentional, rename/document the API and expose an explicit sync policy.

### 6. WAL writes accept short writes as complete records

Location: `src/wal/mod.rs:122-128`

`Write::write` is allowed to return `Ok(n)` with `n < buffer.len()`, but every returned byte count is discarded. The code then advances the logical offset by the full record length, producing a malformed stream while reporting success. This affects the generic `W: Write` API directly and can affect file-backed writes as well.

Encode a frame and use `write_all` (or `write_vectored` with a completion loop), update the offset only after the whole frame succeeds, and return the I/O error instead of panicking.

## P2 — Medium priority

### 7. `compute_async` holds a `DashMap` shard lock across an arbitrary `.await`

Location: `src/key_set_store.rs:164-177`

The occupied entry guard remains alive while user code is awaited. A callback that waits for another operation on the same shard can deadlock, and any slow future blocks unrelated keys in that shard. Cancellation can also leave a partially mutated in-memory set, with no WAL record.

Do not lend a guarded `&mut HashSet` across `.await`. Pass an owned snapshot to the callback, await outside the map guard, then commit the returned result through the same WAL-plus-memory transaction path used by synchronous mutations; define conflict behavior for intervening writes.

### 8. `pop_first` and `pop_last` return the outer map key instead of the removed value

Locations: `src/key_map_store.rs:302-308`, `src/key_map_store.rs:322-328`

Both methods discard the `Vec<u8>` returned by `BTreeMap::pop_*`. They then destructure `store_remove_from_sorted_map_event`, whose first result is the outer collection key, into a variable named `element` and return it. Every successful pop therefore reports `(search_key, outer_key)` rather than `(search_key, removed_value)`.

Retain the value from `pop_first`/`pop_last`, use the WAL call only to log the removal, and return the retained value. Add assertions for both returned values and restart state.

### 9. WAL offsets and frame sizes overflow after 4 GiB

Locations: `src/wal/model/mod.rs:43-45`, `src/wal/model/mod.rs:55-110`, `src/wal/mod.rs:131-135`

Record sizes are truncated with `data.len() as u32`, and the cumulative start offset is a `u32`. A sufficiently large single value or a long-running WAL will panic in debug builds or wrap in release builds. Wrapped footers make backward recovery follow the wrong record boundary and can corrupt replay.

Use checked `u64` lengths/offsets in a versioned format, reject oversized frames before writing, and compact/rotate before a configured limit.

### 10. The public `I128` key variant stores only a `u64`

Locations: `src/model.rs:97-115`, `src/model.rs:173-189`

`Key::I128(u64)` cannot represent negative `i128` values or positive values above `u64::MAX`, while `BytesLen` reports 16 bytes for it. This makes the public type inconsistent with its name and size accounting.

Change the payload to `i128`. Because `Key` is serialized into the WAL, introduce an on-disk format/version migration rather than silently changing decoding of existing data.

### 11. Numeric increment has build-profile-dependent overflow behavior

Location: `src/key_value_store.rs:104-119`

`cur_num + increment_by` panics in debug/test builds but wraps in optimized release builds. A counter near `u64::MAX` therefore behaves differently in production and can persist an unexpected small value.

Use `checked_add` and return a meaningful overflow error, or deliberately use/document `saturating_add` or `wrapping_add`.

## Recommended fix order

1. Define the durability/error contract and make startup/replay crash-safe.
2. Introduce one transaction ordering mechanism spanning WAL and memory.
3. Route all `compute*` and async mutations through that mechanism.
4. Harden framing (`write_all`, checked parser, `u64` offsets, sync policy).
5. Correct the pop return values and numeric key/counter defects, then add restart and concurrency tests.
