## P1 — High priority

### 12. Startup silently accepts a V2 history whose leading segment is missing

Location: `src/wal/replay.rs:335-361`

`checked_v2_replay_frames` validates a segment ID and cumulative base only relative to a preceding segment. It never requires the first segment of a complete history to be segment `0` with base `0`. If `kv.wal.dat.segment-00000000000000000000` is lost from a two-segment store, the remaining active segment starts at ID `1` and a nonzero base, but `try_init_new_with_options` still returns `Ok`. It exposes only the mutations in that remaining segment, silently dropping values whose last record was in the missing prefix. The same behavior applies to set and map stores and to chains whose first available sealed segment has a nonzero ID.

This contradicts the documented startup rule that inconsistent chains must be rejected and preserved for diagnosis: [public-api.md](/work/@projects/penpack-projects/pigment-db/specs/006-v2-wal-segments/contracts/public-api.md:20).

Require a complete replay chain to originate at `(segment_id = 0, segment_base = 0)`. Keep nonzero-first parsing only as an explicit tail-only mode used after the surrounding sealed chain has independently established the active segment's expected ID and base. Add all-family tests that remove the first and a middle sealed segment and assert `InvalidArtifact` without modifying the survivors.

Focused reproduction: create a key/value store with a 170-byte segment target, write `first` and `second` so segment zero seals, delete segment zero, then reopen. The expected `Err` assertion failed because startup returned `Ok`.

### 13. Ordered map append can overwrite an existing element

Location: `src/key_map_store.rs:767-773`

`try_append_ordered_element_core` derives the next numeric key from the first component of the map's greatest overall `SearchKey`. A valid non-`USIZE` key that sorts later makes the method reset to `0`; inserting the append then replaces an existing `SearchKey::from(0usize)` in both live state and the WAL. An empty greatest `SearchKey` also panics at `first().unwrap()`, and `usize::MAX + 1` panics in debug builds or wraps to zero in release builds.

Determine the greatest key in the append method's numeric key domain rather than inspecting the greatest heterogeneous key, use `checked_add`, and return a structured `InvalidData`/`InvalidInput` error when no next key exists. Empty and composite search keys need an explicit, non-panicking rule. Cover mixed key variants, an empty search key, composites, and `usize::MAX` with public tests before changing production code.

Focused reproduction: insert numeric key `0`, insert string key `"last"`, then append. The value at numeric key `0` changed from `zero` to `appended`, and numeric key `1` was never created.

## P2 — Medium priority

### 14. Replay does not enforce the timestamp invariants of an atomic group

Location: `src/wal/replay.rs:425-447` (V2), with the analogous V1 loop at `src/wal/replay.rs:280-305`

Complete-frame validation reads each timestamp bucket, but group validation checks only mutation start, index, and count. It neither requires every member of a group to share one timestamp nor requires accepted groups to be monotonic. A structurally complete record stream with valid per-frame CRCs but contradictory group timestamps therefore reopens successfully, even though the V2 grammar requires timestamps to be identical within a group and monotonic between groups: [wal-v2.md](/work/@projects/penpack-projects/pigment-db/specs/006-v2-wal-segments/contracts/wal-v2.md:28).

Validate one timestamp per complete group, compare each completed group with the previous accepted bucket and the segment base bucket, and apply the same checks during complete replay and migration preflight. Add corruption cases for a mismatched second member and a decreasing later group.

Focused reproduction: create a two-member key/set compute group, change the second member's timestamp, recompute that frame's CRC, and reopen. The expected invalid-artifact assertion failed because both records were accepted.

### 15. CI skips the dedicated tests for several completed fixes

Location: `.github/workflows/recovery.yml:18-47`

The workflow runs a hand-selected set of filtered test commands, but it never executes `tests/v2_wal_segments.rs`, `tests/i128_key.rs`, `tests/numeric_increment_overflow.rs`, `tests/async_compute_conflicts.rs`, or `tests/map_pop_return_values.rs`. These targets contain the primary regressions for Issues #7–#11. The filters compile those targets but do not run their tests, so a pull request can regress the new segment, signed-key, overflow, async-conflict, or pop-value behavior while CI remains green.

Add a matrix-wide `cargo test --all-targets --all-features -- --test-threads=1` step, or explicitly invoke every integration target and keep a manifest test that fails when a new target is not covered. The focused fault-injection steps can remain for diagnosis.
