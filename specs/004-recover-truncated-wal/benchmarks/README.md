# Boundary-Aware WAL Benchmark Protocol

This directory holds immutable pre-feature and final candidate measurements for
the V1 WAL work. Baseline measurements must be captured before production V1
format behavior is enabled and must never be regenerated by the candidate under
test.

## Steady-state matrix

The matrix contains exactly 36 independently evaluated cells:

- stores: `key_value`, `key_set`, `key_map`;
- storage: `vector`, `file`;
- profile: `ordinary_write`, `successful_remove`, `minimal_callback`;
- workers: `1`, `8`.

Each cell uses five warmups and at least eleven measured samples. CSV columns are:

```text
store,mode,profile,workers,samples,ops_per_sample,median_throughput,p95_latency_ns
```

Candidate thresholds are applied per cell: one-worker median throughput is at
least 90% of baseline, eight-worker median throughput is at least 85%, and p95
latency is at most 125%. Faster cells cannot offset a failing cell.

## Startup matrix

The startup report records at least eleven reopen samples for a complete history
containing 1,000,000 accepted operations. Candidate validation pairs that complete
history with the matching terminally torn V1 history and requires the torn median
to be no more than 125% of the complete median.

## Quiet-machine protocol

Before the final candidate run:

1. pause and obtain explicit user confirmation that the machine is quiet;
2. record commit/worktree identity, Rust versions, OS, CPU, filesystem, build mode,
   warmups, samples, and exact benchmark command;
3. stop unrelated CPU-, memory-, and storage-heavy work where practical;
4. run baseline and candidate with identical workload and environment variables;
5. preserve raw rows even when a threshold fails; never edit thresholds after
   observing candidate results.

`baseline.csv` and `baseline.md` are immutable inputs once production V1 work
begins. `final.csv` and `final.md` contain the candidate and paired ratios.
