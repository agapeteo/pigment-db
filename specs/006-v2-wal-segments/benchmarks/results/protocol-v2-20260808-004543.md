## Classification and recommendation

Fixed per-thread affinity eliminates worker migration as the primary explanation, but it does not remove the key/value and key/set lower tail. Each failed candidate sample used `1.23` to `1.52` times its paired baseline worker CPU ticks. The key/map candidate passes comfortably at eight workers and uses fewer median CPU ticks than baseline, which narrows the problem to work performed by the V2 key/value and key/set mutation paths.

Code inspection identifies a focused candidate mechanism: `WalStorage::try_accept_action` constructs a V2 `StoredAction` while holding the exclusive WAL-state lock. Key/value and key/set construction performs payload serialization and CRC work there, extending lock ownership across concurrent writers. Key/map prepares its serialized data and checksum before entering that method, consistent with its stable passing result.

Recommended remediation:

1. Add a deterministic RED unit test proving V2 action construction must occur outside the exclusive WAL-state lock.
2. For V2 only, validate health under a read lock, construct the action, then acquire the write lock, revalidate health, rotate if needed, and append. Keep the V1 path unchanged because its action needs the current offset.
3. Run focused concurrency tests and the complete quality suite GREEN.
4. Build a source-identified fixed-affinity Protocol V3 runner with unchanged workloads and acceptance thresholds, smoke-test it, and pause again before its timed capture.

This is a narrow critical-section reduction, not a global mutex or a weakened benchmark gate. Production code must not change until the remediation is approved.
